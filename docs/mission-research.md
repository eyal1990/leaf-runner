# Periodic mission research

The runner periodically asks its configured `missionReviewModel` to review the selected root as a whole (Terra Medium in the checked-in project, Luna High in the optional example). The shared implementation contains no named mission, mathematical subject, repository layout, or source-provider recipe. Findings about a particular mission live only in that root's versioned research artifacts.

The review is useful when leaf attempts have information that should be combined: repeated counterexamples, circular or invalidated reductions, missing hypotheses, reusable definitions, available proof sources, and missing connections between completed results and the root. It can also collect reference files that isolated proof attempts could not otherwise obtain.

**Scheduling.** `missionReviewEvery` defaults to 100 in `runner-config.json`. The counter is the union of distinct theorem IDs observed by the normal solver graph discovery for this root, including IDs that later disappear from the frontier. Definitions and sketch nodes are excluded. Refreshes, status changes, shrinking frontiers, and revisiting the same ID do not increase the counter. This is a solver observation counter, not the website's full graph-node count: solver discovery stops at completed prerequisites.

The first review is due after 10 distinct theorem IDs (or the configured interval if smaller). If startup discovers an already large graph, one current review covers that observation count; the runner does not generate retrospective reviews for each crossed threshold. The next review requires 100 additional distinct IDs. Nodes observed while a review runs count toward the next review. The counter, pending input and latest completed version survive restarts. A changed root statement, preamble, or Mathlib revision starts a new research context and makes the previous context unavailable to later attempts.

Set `"missionReviewModel": "sol-6.1-medium"` to explicitly select another review profile independently of proof attempts. Use `"missionReviewEvery": 0` to disable reviews, or a different nonnegative integer to change the interval. `--list` performs no research calls or research-state writes. Normal CLI execution uses this feature through the stage pipeline; the legacy whole-theorem embedding/test hook does not schedule reviews.

**Reviewer input and authority.** Each review receives an immutable graph snapshot, the target scope, relevant structured attempt history and diagnostic paths, and the previous research manifest. It must distinguish existing formal proofs, written arguments, and new mathematical work; identify evidence for its conclusions; and label verified observations, inferences and unanswered questions. There is no assumption that an upstream proof exists or uses a particular language or directory layout.

The reviewer returns at most 16,000 characters of Markdown notes and up to five resource URLs with concrete purposes. The runner validates and saves that response. Notes remain advisory: they do not change selection scores, theorem statuses, source definitions, publication journals, proof-validation rules, or dependency environments. Later agents must check the advice against their exact current targets. Research text and downloaded content are treated as untrusted reference data.

**Resources.** The runner downloads public HTTPS resources, with a 4 MiB limit per file and up to three redirects. DNS addresses must be public and are pinned for the TLS connection; each redirect is checked again. Downloads send no platform credentials or cookies. They have a 30-second timeout each, honor cancellation, and are saved without executing code, extracting archives or installing dependencies. Failed downloads are recorded individually so useful notes and other files can still be published. An empty resource list is valid. Reference bytes, final URLs, purposes and SHA-256 hashes are retained in the manifest.

**Agent handoff.** Before each new proof invocation, the serial driver reads the latest compatible completed review and copies its notes and available resources to that attempt's `research-N` directory. It verifies the source hashes before copying and records the review ID, date, paths and hashes in `attempt-context-N.json` under `mission_research`. The shared proof prompt explicitly directs agents to those notes and the resource index. There is no automatic Lean import or assertion that external source code is a proved platform dependency.

Already-running invocations keep their original snapshots. A newer review does not edit them. Another root or an incompatible root context cannot contribute notes. Missing or corrupted optional research is reported and omitted while the proof workflow continues. An old copy never becomes a shared writable reference for another agent.

**Capacity and recovery.** A review reserves one existing CODEX dispatch slot while it invokes the model and saves notes/resources. It uses its own research directory and does not lease a Lean workspace or occupy a theorem job. The model runs in a read-only sandbox and receives no API credentials. It uses the fixed review model independently of a proof `--model` override. Proof/formatting workers and reviews collectively obey the configured Codex cap. Explicitly configured Sol reviews also share the exclusive Sol slot with proof invocations; at most one Sol invocation runs at a time. The checked-in project selects Terra Medium for research; the optional example selects Luna High. See [configuration](configuration.md) for the proof/research distinction and effective settings.

Quota exhaustion parks the review through the existing shared quota controller; it neither consumes a theorem attempt nor acknowledges the node threshold. Normal review failures wait ten minutes before retrying the same saved input. Research has separate invocation counters and numbered answer/prompt/command logs. Completed review counts and errors appear in checkpoints. The selected root completing, its context changing, or runner shutdown cancels obsolete review work. No review result for an obsolete context becomes the latest version.

Research artifacts are under `.runs/mission-research/<root-id>/<context-hash>/<review-id>/`. `state.json` under the root directory records observations and the latest completed pointer. A review's files and manifest commit before that pointer. Interrupted partial versions cannot replace the last completed review.

**Validation and limits.** Automated tests exercise distinct-node scheduling, restart coalescing, retry and quota behavior, configured model/read-only invocation, root/environment isolation, stale-result rejection, file hashes and private snapshots, bounded public downloads and redirected private-address rejection. A pipeline integration test holds the reviewer in a single-slot configuration, then verifies that two subsequent proof agents receive both its notes and a downloaded reference through their real invocation manifests.

These checks establish that the learning loop runs and reaches its consumers. They do not establish an improvement in mathematical success rate. The separate review counters, command timing logs, and per-attempt review IDs make it possible to compare review overhead and later proof outcomes. The default interval is a configurable starting point, not a measured optimum.

Run the focused coverage with `node --test test/mission-research.test.mjs`, or the full offline suite with `npm test`. Integration coverage also checks that root completion cancels an active review, retires queued work safely, and publishes no obsolete notes. Optional compiler integrations require their configured executables. These checks do not invoke a live model review or benchmark production proof success.
